# v0.4.21 性能优化第一轮

## 已解决的浪费

0.4.19 在完全合拢且投影透明时仍持续拉取镜像帧、更新七层模糊纹理、绘制并提交透明帧。动态场景的高刷新渲染路径没有进入空闲状态，应用还会在每个有效霍尔样本上重复执行场景/屏幕计算。

本轮保留 0.4.19 的磁场阈值、角度跟随、画质和动画时间，没有重新引入已回滚的 80 ms 小缝预测。

## 改动

- 效果完全不可见且没有切屏遮罩/待揭示画面时只提交一次透明帧，跳过源图采样、模糊层和渲染。
- 200 ms 内的短暂端点反转保留采集；持续无效果时用 `VirtualDisplay.setSurface(null)` 暂停采集。保留纹理和 EGL 资源，恢复时重新挂接输入并等待新画面。[Android 官方接口说明](https://developer.android.com/reference/android/hardware/display/VirtualDisplay#setSurface(android.view.Surface))明确支持这种暂停方式。
- 渲染进程通过受 shell UID 限制的 Messenger 通知，在有效姿态、显隐、悬停和切屏状态变化时唤醒；空闲 250 ms 轮询只用于租约和漏通知兜底。版本计数避免“检查后、等待前”的通知丢失。开合时仍运行原有渲染节奏。
- 未改变接触状态的霍尔样本只刷新时间戳和磁场，不重复执行全部场景更新。保留 50 Hz 采样、500 ms 失效保护和原有控制器频率。
- 缓存模糊程序属性和 uniform 地址；固定纹理的 FBO 完整性检查只在首次使用时进行；去掉从未使用的全尺寸 scratch[0]，本机 1182² RGBA 约节省 5.3 MiB。
- 每 10 秒记录提交帧、源帧、模糊层重建和遥测次数，用于区分活动和空闲负载。诊断抓帧文件检测不再每帧创建对象/检查文件。

## 实机结果

设备为 lhasa / HyperOS 4.0.11.0。对比两版完全合拢、停在桌面的 `top -b` 采样，各取启动首个汇总之后的两个 5 秒区间；这是 CPU 单核百分比，不是整机耗电比例。

| 进程 | 0.4.19 平均 CPU | 0.4.21 平均 CPU |
| --- | ---: | ---: |
| GPU 渲染辅助进程 | 31.1% | 0.2% |
| 应用进程 | 18.7% | 5.4% |
| 屏幕/霍尔控制器 | 2.1% | 1.7% |

连续纯空闲窗口记录：`presents=0 sourceFrames=0 pyramids=0 polls=40 captureAttached=false`，约 10 秒 40 次兜底遥测。显式 GPU 抓帧为 1,397,124 个全透明像素，投影角度为 0；磁场样本仍新鲜（该帧 28 ms）。

用户已完成“合拢停留后打开小缝、连续快速开合”的测试，并确认“跟手正常，没有异常”。日志记录了外屏打开、内屏平展休眠、折回恢复及切屏画面准备完成。本轮没有量化端到端触摸/铰链延迟，也没有进行长时间电量对照，不能把 CPU 降幅直接宣传为省电百分比。
